# Farmhand 2.0: Instruction Budget and Yielding

**Date:** 2026-08-16
**Status:** Approved, ready for implementation planning
**Supersedes:** Farmhand v1.3.0 step-queue architecture

## Problem

Farmhand throws `Script too complex` at approximately 150 farm plots.

The current architecture (`Program.cs`) builds a `stepQueue` of about 7 delegates and executes
exactly one delegate per tick at `Update10`. A step gets one full tick whether it needs a
fraction of one or ten. There is no way for a step to yield partway through and resume, so any
step whose cost scales with plot count eventually exceeds the roughly 50,000 instruction
per-run budget and kills the script.

At 150 plots, three separate steps independently exceed that budget in their single assigned
tick:

1. **`UpdateBlockState` Phase A** (`Program.cs:412-577`) calls `GetPlotDetails()` once per plot.
   Each call performs a `GetDetailedInfoWithoutRequiredInput()` engine call, a `Split('\n')`,
   and per-line `Substring`/`IndexOf`/`TryParse`, plus roughly 8 `IsFunctional()` calls and up
   to 3 light-property writes.
2. **`RenderGraphicalDisplays`** builds roughly 6 sprites per plot (about 900 sprites) in one
   tick, and calls `GetPlotDetails()` a second time per plot because `SpriteRenderer.cs:393`
   does not reuse what Phase A already computed.
3. **`UpdateBlockState` Phase G** (`Program.cs:712-891`) writes output lines through
   `WriteToMainOutput`, which is O(lines x displays), and each `AppendText` call reaches
   `TextSurfaceProvider.GetActiveScreens()` which performs roughly 8 full `MyIni.TryParse`
   calls.

### Root cause analysis

The instinct is that Farmhand needs Goose's dispatcher. That is only half true. A large share
of Farmhand's per-cycle cost is **redundant work**, not necessary work spread too thin.
Porting the dispatcher alone would spread the same wasted instructions across more ticks
rather than eliminating them.

Ranked bottlenecks, from profiling:

| # | Bottleneck | Location | Scaling |
|---|---|---|---|
| 1 | Unconditional CustomData parse and write per configured block, multiplied by wrapper reconstruction every cycle | `Block.cs:82-127` | O(displays + timers + relays) writes/cycle |
| 2 | `GetActiveScreens()` performs ~8 `MyIni.TryParse` per call; called once per output line | `TextSurfaceProvider.cs:353-376` | O(lines x providers x 8 parses) |
| 3 | Full grid rediscovery every cycle, all wrapper objects reallocated | `FarmGroups.cs:111-258`, `Program.cs:291-383` | O(grid blocks + groups x 8 lookups) |
| 4 | `GetPlotDetails()` recomputed per display instead of shared | `FarmPlot.cs:168-264`, `SpriteRenderer.cs:393`, `PlotLCDRenderer.cs:169,245,479` | O(plots x displays) |
| 5 | Redundant second full pass over plots to count `TotalPlantedPlots` | `Program.cs:694-700` | O(plots), doubled |

**Caching lowers the constant. Yielding removes the exponent.** Farmhand 2.0 does both.
Caching alone would push the wall from roughly 150 plots to roughly 1000. It would still be a
wall, because any O(plots) step with no interior yield point eventually hits it.

## Goals

1. No `Script too complex` error at any farm size.
2. Behavior at small scale is unchanged: a 10-plot farm still completes a full cycle in one tick.
3. Existing `[Farmhand]` custom data configuration keeps working without user migration.
4. Multi-tick scanning must not produce spurious timer, relay, or broadcast events.
5. Pure logic becomes unit-testable so a rewrite of this size has a regression safety net.

## Non-goals

- No shared class library. `Farmhand.Tests` references `Farmhand.csproj` directly, matching how
  `Goose.Tests` references `Goose.csproj`.
- No new farm features. This release is architectural.
- No changes to the visual design of any display.
- No `WorkDispatcher` class. Goose defines one in `Shared/` but its shipped script does not use
  it, inlining the logic on `Program` instead. Farmhand does the same. An abstraction with one
  implementation and one caller is not worth the indirection.

## Architecture

### Pipeline and dispatcher

`Runtime.UpdateFrequency` changes from `Update10` to `Update1`. Space Engineers caps
instructions per run, not per second, so running 60 times per second instead of 6 multiplies
total available throughput by roughly 10x. Each run remains bounded by `BudgetFraction`, so
per-run simulation cost stays capped and predictable.

Steps become `IEnumerator<YieldReason>` generator methods. `RunOneTick` pumps the root iterator
repeatedly within a single tick until the budget trips or the pipeline completes.

```csharp
public enum YieldReason { BudgetHit, ChunkBoundary }

bool BudgetExceeded() {
    return Runtime.CurrentInstructionCount >
           Runtime.MaxInstructionCount * _budgetFraction;
}

void RunOneTick() {
    try {
        do {
            if (_workIterator == null || !_workIterator.MoveNext()) {
                _workIterator = StepRoot();
                break;
            }
        } while (!BudgetExceeded());
    } catch (Exception ex) {
        LogError("step " + _stepIndex + " " + _stepLabel, ex);
        _workIterator = StepRoot();
    }
}

IEnumerator<YieldReason> StepRoot() {
    while (true) {
        // CycleNumber gates every cache in the script, so it must advance
        // here at the top of each pipeline pass. StepRoot never terminates,
        // so RunOneTick's !MoveNext() branch is purely defensive.
        CycleNumber++;
        for (int i = 0; i < StepLabels.Length; i++) {
            _stepIndex = i;
            _stepLabel = StepLabels[i];
            IEnumerator<YieldReason> step = StepFor(i);
            // Explicit MoveNext pump, not foreach, so exceptions in child
            // iterators propagate cleanly to RunOneTick's catch.
            while (step.MoveNext()) {
                yield return step.Current;
            }
            yield return YieldReason.ChunkBoundary;
        }
    }
}
```

The dispatcher self-scales with no configuration or mode switching. On a small farm the whole
pipeline finishes inside one tick, exactly as today. On a large farm it spreads across as many
ticks as it needs.

| 6 | `StepRenderText` | per display |

### Chunking idiom

The loop cursor is a **plain local variable**. Because C# iterator state machines preserve
locals across `MoveNext()` calls, the cursor resumes exactly where it left off with zero manual
bookkeeping. This is the single most important idiom to get right.

```csharp
IEnumerator<YieldReason> StepScanPlots() {
    int counter = 0;
    for (int g = 0; g < _groupList.Count; g++) {
        FarmGroup group = _groupList[g];
        FarmStats scratch = group.ScratchStats;
        scratch.Clear();
        for (int i = 0; i < group.FarmPlots.Count; i++) {
            AccumulatePlot(group.FarmPlots[i], scratch);
            counter++;
            if (counter % 20 == 0) yield return YieldReason.ChunkBoundary;
            if (BudgetExceeded()) yield return YieldReason.BudgetHit;
        }
    }
}
```

Two distinct yield checks with different reasons, following Goose:

- `counter % N == 0` yields `ChunkBoundary`. A cheap cadence-based breathe point independent of
  actual instruction cost.
- `BudgetExceeded()` yields `BudgetHit`. The real instruction-budget check, able to fire on any
  iteration.

Chunked steps only ever walk cached lists. They never call `GridTerminalSystem`.

### Sprite rendering split (steps 7 and 8)

`MySpriteDrawFrame` cannot be safely held across ticks, so graphical rendering splits in two.
The expensive part, computing per-plot layout and building roughly 6 sprites each, accumulates
into a reusable `List<MySprite>` across as many ticks as needed. A single cheap tick then opens
the frame, dumps the accumulated list, and disposes it.

Without this split, a graphical LCD showing a 150-plot group still has to build roughly 900
sprites in one tick. This is the one budget blowout that caching alone does not fix.

The existing `GetOrComputeLayoutRows()` cache in `SpriteRenderer.cs:308` is kept as-is.

## Caching layer

Every cache below is gated on `Program.CycleNumber`, a public `int` property on `Program`
incremented once per pipeline pass in `StepRoot()`. `Block` and its subclasses already hold a
`Program` reference, so no new plumbing is required. Cycle number, not tick number, is the
correct gate: a cycle may span many ticks at scale, and config must stay stable for the whole
of it.

### `Block.cs`: parse once per cycle, write only on change

Today every `GetCustomDataString`/`GetCustomDataBool` getter calls `ParseCustomData()`, which
runs a full `MyIni.TryParse` unconditionally. `UpdateCustomData()` additionally writes
`BlockInstance.CustomData` on every call, and CustomData writes are among the most expensive
operations available to a PB script.

```csharp
int _checkedCycle = -1;
string _lastRaw;

public void ParseCustomData() {
    if (_checkedCycle == _program.CycleNumber) return;
    _checkedCycle = _program.CycleNumber;
    string raw = BlockInstance.CustomData;
    if (raw != _lastRaw) {
        MyIniParseResult result;
        _customData.TryParse(raw, out result);
        _lastRaw = raw;
    }
}
```

Cost becomes one `.CustomData` read plus one string comparison per block per cycle. An actual
INI parse happens only when a player edited the block.

`UpdateCustomData()` guards its write:

```csharp
string rendered = _customData.ToString();
if (rendered != BlockInstance.CustomData) {
    BlockInstance.CustomData = rendered;
    _lastRaw = rendered;
}
```

Updating `_lastRaw` after a self-write prevents the next cycle from detecting our own write as
an external edit and re-parsing needlessly.

**This one change resolves bottlenecks 1 and 2 with no restructuring of call sites.**
`TextSurfaceProvider.GetActiveScreens()` keeps its roughly 8 `ParseCustomData()` calls, but each
becomes an integer comparison instead of an INI parse. No edits to `TextSurfaceProvider.cs`
logic are required.

### `FarmPlot.cs`: cycle-stamped details memo

`GetPlotDetails()` returns live game data, so it is stamped rather than string-compared:

```csharp
FarmPlotDetails _cachedDetails;
int _detailsCycle = -1;

public FarmPlotDetails GetPlotDetails() {
    if (_detailsCycle == _program.CycleNumber) return _cachedDetails;
    _cachedDetails = ParsePlotDetails(_farmPlotLogic.GetDetailedInfoWithoutRequiredInput());
    _detailsCycle = _program.CycleNumber;
    return _cachedDetails;
}
```

`SpriteRenderer.cs:393` and the three call sites in `PlotLCDRenderer.cs` become cache hits with
no edits to those files. Bottleneck 4 resolves for free.

`FarmPlotDetails` is reused rather than reallocated where practical, and the `List<float>`
percentage buffer inside the parser becomes a reusable field.

### `FarmGroups.cs`: reconcile, do not rebuild

Wrapper objects are held in `Dictionary<long, FarmPlot>` keyed by `EntityId` (and equivalently
for the other block types). On rescan, existing wrappers are reused, wrappers are constructed
only for newly seen blocks, and wrappers for vanished blocks are dropped.

Wrapper persistence is load-bearing, not merely an allocation optimization: the two caches above
live on wrapper instances and are meaningless if wrappers are discarded every cycle.

Rescan triggers:

- First run.
- The `rescan` PB command.
- `RescanIntervalCycles` elapsed (default 30).
- Any cached block reports `Closed` during a scan. Nearly free, since scanning already touches
  every block, and it detects deletions immediately.

Goose's FNV drift hash is deliberately **not** ported. It works in Goose because it hashes a
small set of mechanical connections and connectors. Farmhand's equivalent would require
enumerating the grid every tick, which is precisely the cost being removed.

### Config dirty-flagging

PB-level config uses Goose's raw-string comparison, which catches manual player edits without
any explicit invalidation call:

```csharp
IEnumerator<YieldReason> StepParseConfigIfDirty() {
    if (Me.CustomData != _lastSeenCustomData) _configDirty = true;
    if (!_configDirty) { yield return YieldReason.ChunkBoundary; yield break; }
    _lastSeenCustomData = Me.CustomData;
    // full parse and field population
    _configDirty = false;
    yield return YieldReason.ChunkBoundary;
}
```

### Small fixes carried in the same pass

- Fold the redundant `TotalPlantedPlots` pass (`Program.cs:694-700`) into the main plot loop.
- `GetAllGroups()` (`FarmGroups.cs:264-267`) stops calling `groups.Values.ToList()` on every
  invocation. `BuildStepQueue` alone calls it three times.

### Explicitly not cached

Plot water and growth ratios, alert message strings, sprite lists between cycles, and anything
else derived from already-cached details. Once `GetPlotDetails()` is memoized these are cheap,
and caching them would add invalidation bugs for no measurable gain.

## Snapshot commit and event correctness

Once scanning spans multiple ticks, in-place mutation of published aggregates becomes a
correctness bug, not just a cosmetic one.

Goose mutates its published dictionaries in place during chunked scans and accepts torn reads.
Goose can afford this because a sorting script does not care. Farmhand cannot: `StateManager`
fires `OnCropReadyTrue`, `OnWaterLowTrue` and similar events that physically trigger timers,
doors, and sound blocks in-game. A partially accumulated `TotalReadyPlots` would cross a
threshold mid-scan, fire an event, then cross back on the next tick and fire the inverse.

**This is the one place Farmhand 2.0 extends the Goose pattern rather than porting it.**

### Double buffering

`FarmGroup` holds two `FarmStats` instances and swaps references:

```csharp
// StepCommitSnapshot
FarmStats tmp = group.Stats;
group.Stats = group.ScratchStats;
group.ScratchStats = tmp;
```

`FarmStats` gains a `Clear()` method and stops being allocated fresh each cycle
(`Program.cs:397`), which also removes the 5-collection allocation churn per group per cycle.

### Event evaluation moves to commit

All `StateManager.UpdateState()` calls move out of the scan and into `StepCommitSnapshot`,
reading the just-published buffer. Renderers likewise read only the published buffer, never the
scratch buffer.

Invariant: **state transitions are evaluated exactly once per cycle, against a complete
snapshot.**

## Testing

`Farmhand.Tests` is added to `Farmhand.sln` with a `ProjectReference` to `Farmhand.csproj`,
mirroring `Goose.Tests`. Package set: `Microsoft.NET.Test.Sdk` 17.11.1, `xunit` 2.9.2,
`xunit.runner.visualstudio` 2.8.2, `FluentAssertions` 6.12.2, `Mal.Mdk2.References` 2.2.8.
`TargetFramework` is `net48`, `LangVersion` is `latest` for the test project only. The script
project stays at `LangVersion` 6.

Contract for anything under test: `public static`, POCO in, POCO out, no Space Engineers runtime
types. This is exactly how `Goose.Tests/ScopeTests.cs` exercises `Program.BuildScope` via
`Program.MechanicalEdge` POCOs.

### Test targets

1. **`ParsePlotDetails(string) -> FarmPlotDetails`.** Extracted from `FarmPlot.cs:168-264`.
   Highest value target: it is hand-rolled string parsing where malformed input silently
   produces wrong numbers, and it is where the prior non-English localization bug lived
   (commit `ff78da8`). Cases: English input, non-English input, missing lines, empty string,
   malformed numbers, unplanted plot, dead plant, fully grown plant.
2. **Stats accumulation.** `Accumulate(PlotSnapshot, FarmStats)` against a POCO snapshot.
   Covers ready/dying/dead/planted counting and yield summarization without a grid.
3. **State transition rules.** `StateManager` change detection, including the property that a
   partial scan cannot produce a transition.
4. **Light state selection.** Health and water values to color and blink decision, extracted
   from `UpdateBlockState` Phase A.

Discovery, rendering, and the dispatcher itself are not unit tested. They are verified by a
clean build plus in-game testing.

## Configuration

New PB custom data keys under `[Farmhand]`, all optional with defaults:

| Key | Default | Meaning |
|---|---|---|
| `BudgetFraction` | `0.8` | Fraction of `MaxInstructionCount` a single run may consume before yielding |
| `RescanIntervalCycles` | `30` | Cycles between periodic discovery rescans |
| `DebugLogging` | `false` | Enables verbose Echo output |

New PB commands: `rescan`, `pause`, `resume`, `debug on|off`. The existing `cleanup` command is
preserved.

All existing keys and their semantics are unchanged. No user migration is required.

## Diagnostics

Echo output is rendered every `Main` invocation and gains:

- Current step index and label
- Cycle number and ticks consumed by the last completed cycle
- Instruction count, and a high-water mark across the cycle
- Rescan countdown
- A rolling action log and deduplicated warning list, following `Program.Logging.cs` in Goose

The high-water mark specifically exists so that a future report like "it broke at 150 plots" can
be diagnosed without profiling from scratch.

## Implementation phases

Each phase is independently shippable and independently verifiable.

| Phase | Work | Verification |
|---|---|---|
| 0 | Add `Farmhand.Tests`. Extract `ParsePlotDetails` and light-state selection to `public static` with POCO signatures. No behavior change. | `dotnet test` passes; `dotnet build` clean |
| 1 | Caching layer: `Block.cs`, `GetPlotDetails` memo, discovery reconciliation, the two small fixes | Build clean; tests pass; in-game test at 150 plots |
| 2 | Dispatcher, pipeline split into partials, `Update1`, snapshot commit and double buffering, event evaluation moved to commit | Tests pass; in-game confirmation of no event flapping and correct display content |
| 3 | Sprite build/flush split, diagnostics Echo, new config keys and commands | In-game test at 150+ plots; Echo high-water mark stays below budget |

Phase 1 alone is expected to resolve the reported 150-plot failure by roughly 5x to 10x
reduction in per-cycle instructions. Phases 2 and 3 remove the ceiling entirely rather than
raising it.

## Success criteria

1. `dotnet build Farmhand/Farmhand.csproj -c Release` succeeds with no errors and no new warnings.
2. `dotnet test` passes for all four test target areas.
3. A 150-plot farm runs indefinitely with no `Script too complex` error.
4. A 10-plot farm completes a full cycle in a single tick, matching v1.3.0 behavior.
5. Timer, action relay, and broadcast controller events fire exactly once per genuine state
   transition, with no flapping during multi-tick scans.
6. Existing farms configured under v1.3.0 continue working with no custom data changes.
7. Echo reports instruction high-water mark below `BudgetFraction * MaxInstructionCount`.

## Risks

| Risk | Mitigation |
|---|---|
| C# 6.0 constraint. Iterator methods are fine, but tuples, pattern matching, out-variables, and local functions are not available. | `LangVersion` 6 on the script project fails the build on violation. Test project may use `latest`. |
| `Block.cs` write-guard changes when INI default templates get written back. A block whose defaults were never populated now only gets written once rather than every cycle. | Correct by design, but explicitly verify in-game that a freshly tagged block still receives its default template. Covered in phase 1 testing. |
| Wrapper persistence means stale wrappers if `EntityId` reuse occurs after grid operations. | `Closed` check on every scan plus `RescanIntervalCycles` safety net. |
| Splitting `Program.cs` into 7 partials is a large mechanical diff that can hide a behavior change. | Phase 0 tests land before the split. Phases are sequenced so the split (phase 2) happens with tests already in place. |
| `Update1` increases per-second script invocations by 10x, raising baseline simulation overhead even when idle. | `BudgetFraction` caps per-run cost. Steps that are not due (`StepDiscoveryIfDue`, `StepParseConfigIfDirty`) exit immediately. Monitor in-game sim speed during phase 2 testing. |

## Known limitations after implementation

Recorded by the final whole-branch review. None block the release; all are documented so a
future failure report can be triaged quickly.

**The scaling ceiling is raised for the plot scan, not removed everywhere.** Items 1 and 3
below were measured and fixed after the branch was first reviewed; item 2 remains open.

The governing quantity is the **worst uninterruptible chunk**, not the observed peak. The
budget is checked after a chunk runs, never before, so a chunk cannot be interrupted once
entered and the true ceiling is `guard + worst chunk`. The observed peak is only
`guard + whichever chunk happened to straddle the guard`, which is alignment luck and
understates the ceiling. `RunOneTick` measures and reports the worst chunk per cycle for
this reason.

Measured in game on a 28 plot / 22 FarmLCD / 14 PlotLCD farm:

| | worst chunk | ceiling of 50,000 |
|---|---|---|
| As first reviewed | 7,403 (`BuildText`), 7,342 (`Discovery`) | 47,403 |
| After splitting both | 2,200 (`ScanPlots`) | 42,200 |

1. **`BuildMessagesForGroup`** (`Program.Output.cs`). FIXED: now an iterator yielding per
   emitted line, because each line fans out across every display in the group. It scaled
   with plot count rather than group count, which was not obvious from the code shape:
   `AlertMessages` gets one entry per low-water plot and one per dying plot, so it spiked
   precisely during the failure conditions the script exists to report.
2. **`LcdPanel.BuildSprites`**. OPEN. Layout rows are cached but per-plot sprite
   construction is not, so the build is O(plots) per graphical panel. Measured around 1,100
   at 28 plots, which projects to roughly 6,000 at 150 and would make it the new worst
   chunk. This is the highest-value remaining follow-up. `FlushSprites` has the same O(plots)
   shape and **cannot** be split, because a `MySpriteDrawFrame` cannot be held across ticks;
   lowering `BudgetFraction` is the only lever there.
3. **`FindFarmLCDBlocks`** (`Program.Discovery.cs`). FIXED: now an iterator yielding between
   the eight per-group block searches, each of which walks the grid. The earlier claim that
   it "cannot be split" was wrong. Nothing else runs while discovery is in progress, so a
   half-rebuilt group set is never observed by another step. `FindPlotLCDBlocks` is still one
   atomic call, but it is separated from `FindFarmLCDBlocks` by a budget check and did not
   surface as a worst chunk.

**`ScanChunkSize`** (`Program.Scan.cs`) directly sets the `ScanPlots` chunk cost at roughly
110 instructions per plot. At the default of 20 that is the 2,200 above, and unlike the
others it does **not** grow with farm size. Lower it if the scan ever needs to be cheaper.

**Four display indexes have no eviction**: `_lcdPanelsById`, `_textSurfaceProvidersById`,
`_plotLcdsById`, and `_spriteBuffers`. Grinding down and rebuilding a tagged display yields
a new `EntityId`, so the old entry persists for the session. `FarmGroups.Reconcile` does
evict; these do not. Bounded and small in practice, but `_spriteBuffers` retains a whole
`List<MySprite>` per dead panel, which is materially heavier than the others.

**`LcdPanel.DrawGraphicalUI()` is unreachable in live flow.** `StepRenderText` skips
graphical panels, so nothing routes through it. Kept as a fallback API.

**`StepCommitSnapshot` has no automated coverage.** `Program` derives from `MyGridProgram`
and cannot be constructed in the test project, so the buffer swap, the `FarmPlots.Count`
guard, and all nine state conditions are verified by code review and in-game testing only.
This is the highest-risk code in the release; the in-game steady-state timer check is its
only gate.

**Step faults are visible only briefly.** A step that throws is skipped and logged with a
single `Echo` line, which the next `RenderEchoStatus` overwrites. A persistent fault
counter in the Echo would make a wedged pipeline obvious rather than something a user
infers from stale displays.

None. All design decisions are resolved.
